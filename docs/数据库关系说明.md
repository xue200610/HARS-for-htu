# 医院挂号管理系统 · 数据库设计说明

> 对应数据库：`hospital_db`（MySQL 8.0 / InnoDB / utf8mb4），共 **10 张表**、**7 个外键**。
> 配套图：`数据库ER图.png`；可编辑源码：`数据库ER图.mmd`

## 一、实体清单

| # | 表名 | 中文名 | 说明 | 记录数 |
|---|---|---|---|---|
| 1 | `departments` | 科室 | 科室基础信息（名称、主任、床位数、医护人数统计） | 5 |
| 2 | `doctors` | 医生 | 医生档案，用 dept 字段（科室名）归属科室 | 5 |
| 3 | `schedules` | 号源排班 | 号源排班：某医生某天某午别放多少号、已约多少号 | 170 |
| 4 | `drugs` | 药品库存 | 药品库存：数量、单价、库存预警阈值 | 6 |
| 5 | `users` | 用户账号 | 登录账号，三种角色 admin / doctor / patient，患者账号绑定患者档案 | 6 |
| 6 | `patients` | 患者档案 | 患者档案，全院唯一身份（身份证唯一） | 5 |
| 7 | `appointments` | 挂号记录 | 挂号记录（核心业务表），一次挂号一行，带排队号、诊室、费用快照 | 6 |
| 8 | `medical_records` | 门诊病历 | 门诊病历：诊断与处置 | 4 |
| 9 | `inpatient` | 住院床位 | 住院床位：一行 = 一张床，占用时记录患者，空床时患者为空 | 7 |
| 10 | `fees` | 费用结算 | 费用结算单：项目、金额、支付方式、结算状态 | 4 |

## 二、关系清单

### 2.1 已建外键约束（实线，7 个）

| # | 从表.字段 | 到表.字段 | 基数 | 删除策略 | 业务含义 |
|---|---|---|---|---|---|
| 1 | `appointments.patient_id` | `patients.id` | N : 1 | ON DELETE SET NULL | 挂号记录属于哪位患者 |
| 2 | `appointments.schedule_id` | `schedules.id` | N : 1 | ON DELETE SET NULL | 这次挂号约的是哪个号源 |
| 3 | `schedules.doctor_id` | `doctors.id` | N : 1 | ON DELETE RESTRICT | 号源属于哪位医生 |
| 4 | `users.patient_id` | `patients.id` | N : 1 | ON DELETE SET NULL | 患者账号绑定的患者档案 |
| 5 | `medical_records.patient_id` | `patients.id` | N : 1 | ON DELETE SET NULL | 病历属于哪位患者 |
| 6 | `inpatient.patient_id` | `patients.id` | N : 1 | ON DELETE SET NULL | 该床位当前占用的患者（空床为 NULL） |
| 7 | `fees.patient_id` | `patients.id` | N : 1 | ON DELETE SET NULL | 费用单属于哪位患者 |

> `SET NULL`：患者（或号源）被删除时把外键置空、**保留历史单据**；
> `RESTRICT`：医生名下还有号源时不许直接删除，必须先删号源。

### 2.2 按名称关联（虚线，无数据库约束）

| # | 从表.字段 | 到表.字段 | 业务含义 |
|---|---|---|---|
| 1 | `doctors.dept` | `departments.name` | 医生归属科室 |
| 2 | `schedules.dept` | `departments.name` | 号源的科室名（冗余，便于按科室筛号） |
| 3 | `schedules.doctor` | `doctors.name` | 号源的医生姓名（冗余快照） |
| 4 | `appointments.dept / doctor` | `departments / doctors.name` | 挂号时的科室、医生名（快照） |
| 5 | `appointments.patient_name` | `patients.name` | 挂号时的患者姓名（快照） |
| 6 | `medical_records.doctor / dept / patient_name` | `doctors / departments / patients.name` | 病历中的名称快照 |
| 7 | `inpatient.doctor / dept / patient_name` | `doctors / departments / patients.name` | 住院记录中的名称快照 |
| 8 | `fees.patient_name` | `patients.name` | 费用单中的患者姓名快照 |


## 三、设计说明

### 3.1 为什么外键都用 SET NULL 而不是 CASCADE
挂号记录、病历、费用单都是**历史凭证**。患者被删除时若级联删除，历史统计（挂号量、收入）会凭空消失，
所以选择「外键置空、单据保留」，统计时用名称快照兜底。

### 3.2 名称冗余与一致性保证
`appointments`、`medical_records`、`inpatient`、`fees` 除了存 `patient_id`，还冗余存了 `patient_name`、`dept`、`doctor`。原因：
1. 单据能显示当时的姓名；
2. 列表查询不用多表 JOIN，性能好。

但姓名在本系统里**同时承担业务标识的角色**：医生登录账号 `users.name` 存的就是医生姓名，
医生端「我的挂号」正是按姓名筛选（`WHERE doctor = ?`）。因此改姓名不能只改一张表，
后端在修改医生 / 患者姓名时，会把所有引用该姓名的表一并同步：

| 改谁 | 同步范围 |
|---|---|
| 医生 | `doctors` → `schedules.doctor`、`appointments.doctor`、`patients.doctor`、`medical_records.doctor`、`inpatient.doctor`、`users.name`（医生登录账号） |
| 患者 | `patients` → `users.name`（患者登录账号）、`appointments.patient_name`、`fees.patient_name`、`medical_records.patient_name`、`inpatient.patient_name` |

同步优先用 `patient_id` / `doctor_id` 精确定位；只有桌面端早期数据（无 id 关联）才按「旧姓名」兜底，
并要求旧姓名在该表里唯一，避免误改同名的人。

两个注意点：
- 改名后**该账号需要重新登录**（JWT 令牌里存的是登录时的姓名）；
- 用姓名当业务标识是这套设计的弱点，规范做法是给 `appointments` 等表加 `doctor_id`，用 id 关联、姓名只用于展示。

### 3.3 科室为什么不建外键
`departments.name` 是**业务主键**，`doctors.dept`、`schedules.dept`、`appointments.dept` 存的是科室**名称**而非 id。
好处是查询展示直接，代价是改科室名要同步三张表（后端已实现该同步）。若要更规范，可改成 `dept_id` 外键。

### 3.4 已知的可改进点
| 问题 | 现状 | 建议 |
|---|---|---|
| 日期时间用 varchar 存 | `appt_time`、`record_date`、`admit_date`、`fee_time` 都是字符串 | 改为 `DATETIME` / `DATE`（需同步改桌面端显示代码） |
| `patients.age` 存年龄 | 年龄每年会变，长期会失真 | 增加 `birth_date`，年龄由出生日期计算 |
| 药品与就诊无关联 | `drugs` 是孤立表，没有处方表 | 增加 `prescriptions` + `prescription_items` |
| 缺操作日志 | 挂号/取消/接诊的留痕只在服务内存里 | 增加 `audit_logs` 表 |
| 床位与住院记录混在一张表 | `inpatient` 一行既是床位又是住院记录，空床用 NULL 患者表示 | 拆成 `beds` + `admissions` |
